# Design: M2 Living world

## Context
See proposal.md and `docs/research/playerbots-scripting.md` (sections 1, 2, 4 and 5) for what mod-playerbots can do headlessly.

## Decisions
- **Profiles in config.py.** `profile="m0"` keeps 10 bots for fast tests. `profile="population"` sets N random bots plus level/zone distribution and activity knobs (e.g. `BotActiveAlone`, SmartScale, teleport intervals). The builder picks the exact keys from `playerbots.conf.dist` and documents each one. Checks that need population bring the stack up with that profile; the runner orders them so that one warm-up serves `pop.*` and `perf.*`.
- **Zone mapping.** Read `AreaTable.dbc` (WDBC reader exists in `tools/era-diff/era_diff.py`; move it into `harness/hslib/dbc.py`). Starting zones and capitals are identified from DBC/`game_tele` data, with the selection rule written in the check; never from memory.
- **Probe chat.** Add CMSG_MESSAGECHAT (say/party/whisper) and SMSG_MESSAGECHAT parsing to `harness/hslib/probe/`, with opcodes and layouts taken from AC source. Companion checks run the probe as a GM-level account (playerbots grants GM senders full control).
- **Moving the master.** A GM teleport of the test character (`.tele name`) stands in for walking. Follow is measured by bot position (the `.pinfo`/`.gps`-style output over SOAP, or the probe's received movement updates; the builder chooses and documents).
- **World-update time.** Use the server's own metric: `.server info` reports update-time diffs in AC. If it doesn't expose a p95, sample it every 10 s and compute the statistics over the window.
- **Tuning record.** `docs/research/m2-population-tuning.md`: one row per measured N with peak and median metrics, picking the largest N within the budget.

## Notes from later work (2026-10-02)
- Upstream server-mail login crash is fixed by core patch 0001 (ADR-0006); bots logging in and out are safe from it.
- `fixtures.settle_login` requires `CharacterDatabase.WorkerThreads = 1`; if the population needs more DB workers, remove settle_login (core patch makes it non-essential) rather than weaken its barrier.
- Keep the Mac awake during long runs (F12): wrap warm-up/sampling in `caffeinate` or an IOPM assertion; a mysqld stall was seen during display sleep.
- Tag population/perf checks `slow`; companion checks can be `full` if they take < ~2 min.

## Risks
- Warm-up time grows full runs by about 10 minutes. → Acceptable; one shared warm-up.
- Bot behaviour is stochastic. → Thresholds use generous percentages and evidence keeps the raw samples; flakiness counts as P0, so tune the thresholds or knobs with recorded reasons.
- 16 GB is tight with the client running. → The budget reserves 3 GB host memory for the client; the human scenario confirms it.

## Builder notes, tasks 1.0 / 1.1 / 2.1 / 4.1 (B12, 2026-10-03)

### Slow-tier rule (1.0)
`runner.slow_tier_skips` lists the slow checks referenced by a gating scenario (archived specs + `harness/active-changes`). A **full**-tier run records each as `skip` with the message `slow tier, not run in a full run` and lists them in `meta.slow_tier_skipped`. `runner.tolerated_skip` accepts such a record only when the run's tier is `full`, the registry says the check is `slow`, the runner listed it, and the message matches. `reporting.full_run_record` leaves those records out of `non_passing`. A slow run executes them like any check. Any other skip still fails. `report.slow_tier_rule` (quick) drives the runner's own functions (`select`, `slow_tier_skips`, `execute`, `full_run_record`, `run_ok`) over a synthetic registry, covering five cases: a full run, a slow run that passes, a slow run that fails, a full check that skips, and a full check that imitates the slow-skip message.

### Profiles and helpers (1.1)
- `harness/hslib/config.py` `PROFILES`: `m0` (10 random bots, the default) and `population`. Select one with `hs up --profile population`, `HS_PROFILE=population` (also read by `./play` and `hs launch`, since they call `stack.up`), or `stack.up(profile=…)` in code. A check declares `@check(..., profile=…)`. `stack.up` records the running profile and a digest of its overrides in `env/run/stack-profile.json`. The runner restarts a worldserver that runs a different profile (`stack.ensure_profile`). `hs up --profile X` refuses when a worldserver already runs with another profile.
- `HS_POPULATION_N=<n>` renders the population profile at another N. It is for tuning runs only: `perf.population_tuned` fails a session whose N isn't `config.POPULATION_N`.
- `harness/hslib/botlog.py`: `offset/lines/grep/count` over `env/logs/Playerbots.log`, which is truncated at each worldserver start.
- `harness/hslib/dbc.py`: the WDBC reader moved from era-diff (era-diff imports it), plus `area_table()` and `top_zone()`.
- `util.keep_awake`: `caffeinate -i -d -u -w <pid>` around every `hs run` and every population session (F12). The session evidence includes the `pmset -g assertions` lines for that pid.
- mysqld (`stack._write_my_cnf`, every profile): `performance_schema=OFF` and `innodb_log_buffer_size=16M`. Measured with the M0 profile, mysqld's memory footprint dropped from 1.01 GB to 0.70 GB, under the 1.0 GB budget. Nothing reads performance_schema.

Single runs vary a lot. Bots reach a capital in a burst at boot and leave within minutes by flight, grinding or quests. A capital's count at any moment is roughly inflow × residence time, and at N=300 its minimum swings between 0 and 4. See "Open: capital coverage" below.

**Fresh world at every population start** (`population.fresh_start`, called by `stack.up` before the worldserver starts, population profile only). mod-playerbots stores each bot's level and its next randomize and teleport times (teleport every 1-5 h, randomize every 2 h to 14 d). Without a reset, each boot resumes bots where the last session left them. Measured: a second session at N=250 had 0-2 bots in 7 of the 8 capitals, because bots had walked out and their teleport timers hadn't expired. Over accumulated play, bots also level out of the starting zones. The step sets random-bot characters to level 1 and deletes their `randomize`/`teleport` timer rows. Seconds after login, `Randomize()` then takes the `RandomizeFirst` path: a new level from the knobs above, then a teleport for that level. In gameplay terms, every time the server starts the ambient bots re-roll like a fresh realm, while names, races and classes persist. It touches only characters on accounts with `playerbots_account_type = 1`. `pop.size_stable` compares checksums of non-bot accounts and characters before and after.

### Zone targets (data rule, never memory)
- **Starting zones:** for each race in `world.playercreateinfo`, take the start zone shared by most of its classes (this outvotes the Death Knight start), then map it to its top-level zone through `AreaTable.dbc` parents. Races that share a zone count once.
- **Capitals:** `AreaTable.dbc` zones (parent 0) with `AREA_FLAG_CAPITAL` 0x100 (`DBCEnums.h:242`) and team ALLY (2) or HORDE (4) (`DBCEnums.h:56-59`). This drops the neutral, capital-flagged Shattrath and Dalaran (team 6).
- A bot's zone is `characters.zone` after `.saveall` (the zone the server computed from its position), mapped to its top-level zone through `AreaTable.dbc`. The `.saveall` barrier: every online bot's `totaltime` (played seconds, written by `Player::SaveToDB`) must advance.

### Session and timing
`population.run_session`: stack down → `hs up --profile population` (T0) → 570 s warm-up → S0 (its `.saveall` must start within 600 s of T0) → S1 300 s later. Meanwhile a sampler thread takes one sample every 10 s for 600 s. All five checks read the same session (`ctx["population_session"]`). They run at order 400+, after every m0 check.

### Process memory metric
The budget's "resident memory" is measured as **max(ps RSS, `proc_pid_rusage` phys_footprint)**, which is the conservative reading. This Mac runs with 7-8.5 GB of swap in use, because of other apps. macOS compresses and swaps idle server heap, so RSS reads far below real use. Measured: worldserver RSS 0.75 GB against a footprint of 3.30 GB, with `vmmap` showing 3.0 GB allocated at 0% fragmentation. Footprint is the "Memory" column in Activity Monitor. Both figures are in every sample.

### Open: capital coverage and the budget (for the orchestrator)
- **Capital coverage at N=300 is marginal.** Starting zones hold with margin: 7 to 31 bots each in every measured fresh-start run. The 8 capitals, though, hold a minimum of 0-4 bots at the ~570 s snapshot depending on the run (table above). The knobs that raise it are more bots (`N`, which costs memory), a longer stay (RPG status weights, which would change bot behaviour everywhere) or faster refill (a shorter teleport interval, which pulls bots out of the leveling zones). None was taken further, per the orchestrator's instruction to stop at the budget conflict.
- **The budget conflicts with coverage.** Worldserver memory (max of RSS and footprint) is above 4.0 GB at every measured N, including N=50 (4.21 GB). The full table is in `docs/research/m2-population-tuning.md`. Host free+inactive memory is set by the other apps on this Mac.

## Builder notes, task 2.2 (B12, 2026-10-03): world-size setting, ~500 default, revised budget
- **Setting.** `harness/hslib/settings.py` reads `env/settings.json` (env/ is gitignored), or `$HS_SETTINGS` when set: `{"world_size": "small" | "normal" | "large" | <bots>}`. A missing file or key means `normal`. Change it with `harness/hs world-size small` (no argument shows the current value), or by editing the file. Presets live in `config.WORLD_SIZES`: small 150, normal 500, large 1000. The measurements behind them are in `docs/research/m2-population-tuning.md`. A numeric size must be 10-2000.
- **`./play`** (`play.py` → `settings.play_world()` → `launch.prepare(profile, population_n)` → `stack.up`) starts the population profile at the configured size. An explicit `$HS_PROFILE` wins, and then the settings file isn't read. `stack.up(population_n=…)` renders N, and `env/run/stack-profile.json` records `n` and a digest that covers N. `hs launch` and plain `hs up` still default to m0.
- **Checks never read the user's setting.** `play_checks` run `./play` with `HS_PROFILE=m0` pinned. The population checks use `config.POPULATION_N` (= the normal preset). `pop.size_setting` uses a scratch settings file through `$HS_SETTINGS`.
- **`pop.size_setting`** (slow, order 395, its own short boot before the main session). With no settings file, `play_world()` must resolve to population at normal. With a scratch file set to `small`, it calls the same `settings.play_world()` → `stack.up(profile, population_n)` path as `./play`. It then requires: a running profile of population with `n`=150 and a matching digest; online random bots within 5% of 150 for 3 consecutive polls 10 s apart, within 420 s. Login took about 1-2 min. The check adds about 3 minutes to a slow run.
- **`pop.fresh_start_scope`** (slow, shares the main session). `fresh_start` now records the non-bot checksums before and after its own SQL, the bot level histogram after the reset, and the randomize/teleport timer rows left. The check requires: all random-bot characters (at least N) at `FRESH_LEVEL` 1; 0 timer rows left; identical non-bot checksums across the reset and across the whole session. On the first boot after raising N, the new bot characters are created after the reset (they start at level 1 anyway), so `reset < N` fails that one run. The slow run never hits this, because the 1500-character pool already exists.
- **Budget** (`population.LIMITS`): worldserver 6.0 GB, mysqld 1.0 GB, stack total (worldserver + mysqld + authserver) 7.0 GB, p95 100 ms, median 50 ms. Host free+inactive is in `RECORDED`: summarized in evidence but not limited.
- **Capital weights at N=500.** With weight 1, Stormwind, Orgrimmar and Silvermoon held 5, 5 and 6 bots, against 13-15 for the weight-2 cities and 12-15 for Darnassus and Exodar. Final setting: every base capital at weight 2 except Darnassus and Exodar (1) and Thunder Bluff (4). At equal weight, Thunder Bluff's intake 60 s after start was 11 against 17-25 for the other Horde capitals, and it held 2 in one slow run; its banker spawns are valid (`creature` rows on map 1, z≈128). Capital minimums at about 570 s: 12 at N=750; at N=500 see the tuning record.

### Companion checks (3.2)
- **Driver:** `hslib/companion.py`. Account `HSCOMP` (`paths.COMP_USER`) created with SOAP `account create` and given security level 2 with `account set gmlevel` (RBAC role 193 links `RBAC_PERM_COMMAND_GM` 371, so playerbots grants ALLOW_ALL, plus `.go`, `.summon`, `.npc info`, `.gps`, instant logout). Character `Hscomp`, human warrior, created with the probe's CMSG_CHAR_CREATE. HSTEST and PLAYER are never used; `play.py` refuses `HSCOMP` as a personal account name, like HSTEST and HS_GM. Each session levels the master to 8 and places it with `.tele name` while offline, logs in, types `.gm off`, revives it if an earlier session left it dead, and leaves any party left over. On exit it removes online companions, leaves the party, `.combatstop`, and logs out.
- **Companions:** `.playerbots bot addclass <class>` and `.playerbots bot remove <name>`, typed as chat (syntax: `vendor/mod-playerbots/src/Bot/PlayerbotMgr.cpp` HandlePlayerbotCommand). The bot comes from the addclass pool (`playerbots_account_type` 2), joins the party through OnBotLogin's GroupInviteOperation, and is re-rolled to the master's level. After it joins, the master whispers `reset botAI` (ResetAiAction), because strategies a master changes persist per bot in `playerbots_db_store` and come back at its next login. A counterexample that made a pool bot passive kept failing later runs until this reset was added. The checks test companions with their default strategies.
- **Data rules (never memory):** quest = `companion.QUEST_RULE` (quest 52 at this pin); creature = `companion.CREATURE_RULE` (FactionTemplate.dbc hostileMask & FACTION_MASK_PLAYER, rank 0, level master-3..master-1, nearest live spawn); follow points = `companion.FOLLOW_RULE` (no hostile spawn within 40 yd of the path; game_tele LakeEverstill → Lakeshire, 128 yd at this pin. The first pair, ElwynnForest → CrystalLake, failed once in a slow run: the companion stopped 33 yd short for 45 s, fighting near the path). Each rule's text is in the evidence.
- **How each THEN is read:**
  - `comp.add_remove`: SMSG_GROUP_LIST to the master lists a new member with the online flag whose `characters.class` is 5 and whose account is in the addclass pool, within 30 s. After `.playerbots bot remove <name>`, that member must be gone from SMSG_GROUP_LIST within 30 s.
  - `comp.follows`: live positions from `.gps` with the selection set to the master and then the companion (ChatHandler::getSelectedUnit). The companion must be within 15 yd before the move. SOAP `.tele name Hscomp <point>` then moves the master at least 100 yd, with the same map and zone per `.gps`. The companion must then be within 15 yd (3D) within 60 s. Measured: about 22 s on the current pair, 4 of 4 runs.
  - `comp.assists`: warrior companion. `.go xyz` puts the master on the picked creature's live position (`.npc info <spawn>`), and the probe then sends one MSG_MOVE_HEARTBEAT at the landing point, as a client reports its position. The creature rule requires no other hostile spawn within 30 yd: with packs nearby, the companion often fought an add for more than 20 s. "The master enters combat" means the first creature that hits or starts attacking the master (SMSG_ATTACKSTART or a combat-log hit), and it must match the creature rule. The master then selects it and sends nothing but chat (`.summon`, `.npc info`). The companion must attack it (ATTACKSTART or combat log, attacker = companion) within 20 s. The creature must reach `.npc info` health 0 within 60 s, which is the check's own bound because the spec gives none; measured about 8 s. The master's damage to it must be 0.
  - `comp.quest_shared`: the master gets the quest with `.quest add` and the companion is cleared with `.quest remove`. The master sends CMSG_PUSHQUESTTOPARTY, and SOAP `.quest status <id> <companion>` must read Incomplete or Complete within 30 s.
- **Tier:** `full`. Each check takes 35 to 65 s.

### Open: two scenarios fail on the pinned build (product gaps, not check problems)
1. **`.playerbots bot remove` leaves the companion in the party as an offline member.** LogoutPlayerBot (PlayerbotMgr.cpp:350) queues BotLogoutGroupCleanupOperation (`Script/WorldThr/PlayerbotOperations.h:418-438`), which only saves strategies. It doesn't remove the bot from the group, and the core keeps logged-out members. Measured: SMSG_GROUP_LIST still lists the bot (online=false) 30 s and more after the command. Whispering `leave` to the bot does remove it from the party (LeaveGroupAction → CMSG_GROUP_DISBAND), but it stays online. Options for the orchestrator: a module patch (remove from the master's group on `remove`), a documented two-step removal (spec change), or accepting the offline slot.
2. **Shared quests never reach companions.** mod-playerbots learns of the master's share through the `OnPacketReceived` hook, which runs *after* the core handler (`Server/WorldSession.cpp:467-474`, `#ifdef MOD_PLAYERBOTS`). CMSG_PUSHQUESTTOPARTY has a typed handler (`Opcodes.cpp:544`), and `PacketHandler::Call` move-constructs the typed packet from the WorldPacket (`Protocol/Opcodes.cpp:31-36`). The ByteBuffer move constructor empties the source (`shared/Packets/ByteBuffer.h:85-90`). The hook therefore gets an empty packet, `PacketHandlingHelper::AddPacket` drops it (`PlayerbotAI.cpp:103-111`), and the "quest share" trigger never fires: no `T:quest share` appears in Playerbots.log, while the server answers SHARING_QUEST and sends the quest details to the bot. Fixing it needs a core patch (copy the packet for the hook when MOD_PLAYERBOTS) with an ADR. Other typed-handler opcodes that bots watch through the same hook are probably affected too (not audited).

### Resolution of the two gaps (orchestrator decision 2026-10-03: fix, no spec change)
- **Quest share:** core patch `patches/core/0002-playerbots-hook-packet-copy.patch` (ADR-0007, proposed). The `OnPacketReceived` hook now gets a copy of the packet taken before the handler runs. The ADR audits every opcode the hook feeds to bots: CMSG_PUSHQUESTTOPARTY and CMSG_QUEST_CONFIRM_ACCEPT were broken, and both are fixed.
- **Remove:** a new mod-playerbots patch queue `patches/playerbots/*.patch`, applied by `build.sync_vendor`, pin-enforced (`patched_pin_state` for playerbots, `build.pin_enforced`), and part of the build-input hash (`patches_playerbots`; `build.clean_smart` has a sandbox flip case). `patches/playerbots/0001-remove-bot-from-group-on-logout.patch` (ADR-0008, proposed) makes `.playerbots bot remove` take the bot out of its party after the logout, disbanding a 2-person party.
- **Coverage:** `core.playerbots_patches_applied` (quick) checks that both patches apply to their pins, that every hook site is patched and the remove path is in place, in the pristine and the vendor tree, that both trees are sha + their queue, that the installed stamp names both patches, and that editing either patch flips the input hash.
- **Keep-awake (F12):** `util.keep_awake` now runs `caffeinate -s -i -d -u -w <pid>`. `-s` holds PreventSystemSleep on AC power. A MacBook with its lid closed and no external display can still go to "Clamshell Sleep" (it happened 2026-10-03 05:30 during a run, and worldserver stalled for 5 min). Keep the lid open during long runs.

## Builder notes, verifier follow-ups (B14, 2026-10-03)

### `core.login_logout_race_baseline`: this run's own backtrace
- **Source of the frames.** `harness/hslib/crashtrace.c` is a small shim that the check compiles into `baseline/tmp/crashtrace.dylib` and injects into the baseline worldserver with `DYLD_INSERT_LIBRARIES`. dyld honours this because the binary is ad-hoc linker-signed without the hardened runtime. The shim installs a SIGSEGV/SIGBUS handler. When the crash happens, the handler writes `baseline/tmp/crashtrace/crash-<pid>.txt` from inside the dying process: the signal, the arm64 exception state (ESR, FAR), the main executable's LC_UUID and slide, and the faulting thread's pc plus its frame-pointer chain. It then restores SIG_DFL and re-raises, so the process still dies of SIGSEGV. `crashtrace.py` symbolizes the frames with `atos` against the binary file. lldb was the first choice, but `lldb --batch` hung waiting for debugger authorization, because Developer Mode is off on this Mac.
- **What the check requires**, all from this run: the shim is loaded (`lsof`); the process crashed; `returncode == -11`; a complete record whose pid is the baseline process's pid (earlier records are deleted before the start); signal 11; the record's UUID equals `dwarfdump --uuid` of `baseline/server/bin/worldserver`; ESR exception class 0x24/0x25 (a real data abort); and the top frames name `ServerMailMgr::SendServerMail` or `ServerMailReward::OnPlayerLogin`. A fresh `.ips` for the pid is recorded only as `supplementary_ips_reports` and never gates the check. Nothing in `~/Library/Logs/DiagnosticReports` is moved, edited or deleted.
- **Telling a fault from `kill`.** On this macOS, `kill -SEGV` arrives with `si_code` 2 (SEGV_ACCERR) and `si_pid` 0, exactly like a real null dereference, so siginfo can't tell them apart. The ESR exception class can: a real fault is 0x24, and an idle process that gets killed is 0x15 (SVC: the thread was in a syscall).
- **Counterexamples** (driver `harness/out/b14/cx_baseline.py`, which monkeypatches the check module): (a) `kill -SEGV` of the idle baseline gives returncode -11 and ESR class 0x15, and the frames are `WorldUpdateLoop`/`main` → FAIL "not a bad-access fault". (b) No crash, with the stale `.ips` still present and a stale crashtrace record planted → FAIL "survived 0 attempts". (c) A real race crash, but the expected UUID is swapped for another → FAIL "main image UUID is not the baseline worldserver's".

### ./play and an already-running stack; `pop.size_setting` takes ./play's path
- **Decision: restart, don't keep the wrong world.** Before this change, `launch.prepare` skipped `stack.up` whenever all three processes were running. So `./play` after `hs up` (or after a harness run) kept the 10-bot m0 world, or a living world of another size, without saying so. Now the stack step is `launch.ensure_world(profile, population_n)`. When ./play asks for a world (it always does: `play.choose_world()`, from the settings file or a pinned `$HS_PROFILE`) and the running worldserver's recorded profile, N or digest differ (`stack.world_matches`), it says "The game server is running the 'm0' test world, not the living world with 150 AI players; restarting the world server..." and restarts only the worldserver. mysqld and authserver keep running. The fresh-world reset runs as on any population start. Restarting is consistent with ./play's exit, which already stops whatever stack it found. A worldserver started outside the harness has no matching record, so it is restarted too. `hs launch` passes no profile and keeps whatever runs, as before. In player terms, ./play always gives you the world size you set.
- **The check.** `pop.size_setting` calls the same two functions that ./play's `Loop.run` calls: `play.choose_world()` and then `launch.ensure_world()` (the stack step inside `launch.prepare`). `$HS_SETTINGS` points at a scratch file saying `small`, and `$HS_PROFILE` is unset. It leaves out only the client-side steps (Wine prefix, client config, Wow.exe). It runs two GIVEN states: `running_m0` (a 10-bot m0 stack started first, like `hs up`) and `cold`. Each requires: ./play chose population at N=150 from the scratch file; the running profile is population with n=150 and the matching digest; online random bots stay within 5% of 150 for 3 polls 10 s apart, within 420 s; and the restart was reported in `running_m0` and absent in `cold`. The no-file case calls `play.choose_world()` with `$HS_SETTINGS` pointing at a missing file and must get normal (500).
- **Why not the full ./play with the stand-in client.** That was B14's first version. On 2026-10-03 around 12:55 local time, every Wine process on this Mac (even `wine --version`) hung in uninterruptible wait (`U` state, unkillable) while Rosetta-launching the x86_64 Wine runtime. That is a host problem outside the repo, and it would have made the population check depend on the client layer. The play.* checks still cover the client half of ./play.
