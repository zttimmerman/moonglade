# Design: test-loop speedups

- **Preflight:** `runner.gui_rule()` already decides whether GUI-marked checks run. `guienv.preflight_problem` takes that decision into account: locked or asleep only matters when the GUI checks are due.
- **Keep-awake:** `caffeinate -d -i -w <hs pid>`, started at the beginning of the run, ends with the run on its own, even after a SIGKILL. The check reads `pmset -g assertions`.
- **Last full run:** copied in `post_run` when `full_run` is true. The timing baseline reads it by default.
- **Orphans:** each harness run records its pid and its children's process group in a run file under `env/run/`. On the next start, a run file whose harness pid is dead marks the recorded processes as orphans. They are stopped with the existing stop path, `./play`'s SIGTERM handler, then `hs down`. A `./play` without such a record is the player's and is never touched.
- **Nightly:** `hs nightly` → 3× `hs run --tier full`, with each `results.json` copied to `harness/out/nightly/<date>/run<n>.json`, then `flakes.md`. A LaunchAgent plist goes in ~/Library/LaunchAgents only with `--install`.
- **Faster full run (B36):** first measure per-check wall time and which exclusive resources each check uses (stack up/down, client/Wine, screen, ports, DB fixtures). Then run the resource-free and stack-sharing groups concurrently where safe. If 25 minutes isn't reachable safely, report the measured best and the blockers. Don't weaken the requirement.

## As built
### B35 (tasks 1.1-1.5)
- **Preflight (1.1):** `runner.gui_preflight_decision(tier, only, ignore, probe, rule_fn)` returns `{guarded, state, gui_due, gui_rule_changed, refuse}`. `gui_due` is always true for `--tier gui`; for full/slow it is `gui_changed(gui_rule())`, which fails closed when the rule is unknown. `guienv.preflight_problem(state, gui_due)` counts the screen lock and display sleep only when `gui_due` is true; low battery on battery power always counts. The CLI prints the one-line refusal and exits 2 before `run()` is called. Otherwise the decision is stored in `meta.gui_preflight` (and `ctx`), so the probed screen state is part of the run's evidence. Test switches (`guienv.PREFLIGHT_TEST_ENV`): `HS_TEST_GUI_PROBE` (stub probe JSON), `HS_TEST_GUI_RULE` (changed | unchanged | unknown) and `HS_TEST_PREFLIGHT_ONLY` (print the decision and exit 0 instead of running). The CLI refuses all three with exit 2 unless the command is `run` and `$HS_HARNESS_RUN=1`. Check: `report.gui_preflight` (quick) runs 16 in-process cases plus 5 nested `hs run`s. The nested runs always carry the decision-only switch, so a broken preflight can never start a real run from inside a check.
- **Keep-awake (1.2):** the existing `util.keep_awake` (`caffeinate -s -i -d -u -w <hs pid>`, F12) already wrapped every `hs run`. Its `-d` is the PreventUserIdleDisplaySleep assertion, `-w` releases it after a SIGKILL, and `__exit__` releases it on an error. The new piece is `hs keep-awake [--hours N]` (`util.keep_awake_cli`): it execs `caffeinate -s -i -d -u -t N*3600` (0 < N <= 24, default 8), so stopping the process releases the assertion. Check: `report.keep_awake` (quick). It confirms this run's own assertion during the check. It then runs three nested `hs run`s (ok, error, SIGKILL), each frozen with SIGSTOP once its caffeinate exists so the assertion can be read deterministically, and requires every assertion to be gone within 5 s of the run's exit. The error run errors because its results.json path is a directory. Finally it checks `hs keep-awake --hours 0.002`, both timed out and SIGTERMed.
- **Last full run (1.3):** `runner.write_outputs` writes results.json and summary.md. When `keeps_last_full_run(meta)` holds (`full_run` true, tier `full`, no filter), it also writes them atomically to `runner.LAST_FULL_RUN` = `harness/out/last-full-run/`. Slow runs don't count: the timing baseline only accepts full-tier runs. `hs timing-baseline join [results] --label X` defaults to `last-full-run/results.json` (`timingbase.default_results`). It exits 1 with a message naming that path when the file is missing, and the hidden `--baseline` lets the check join into a scratch copy. Check: `report.last_full_run` (quick) runs a sequence of stub documents through `write_outputs` into a scratch last-full-run dir, joins the kept copy into a scratch baseline, runs `hs timing-baseline join` without a path, and validates the live copy if one exists.
- **Orphans (1.4):** `runreg.py`. `hs run` writes `env/run/harness-runs/<pid>-<start time>.json` (the process start time, from the new `procs.start_time`, guards against pid reuse) and exports `HS_HARNESS_RUN_ID` to its subprocesses. The file is removed in a `finally`, so only a kill leaves it behind. At the start of every run, `runreg.heal()` looks for dead runs and the processes still carrying their id: `HS_HARNESS_RUN=1` plus that id in the process's initial environment, read from KERN_PROCARGS2; the healer itself and its ancestors are excluded. It stops them in this order: SIGTERM to ./play, whose handler cleans up (waits up to 150 s); `launch.stop_prefix()`, only if every prefix process is an orphan; `stack.down()`, only if every stack process is an orphan; then SIGTERM and, after 10 s, SIGKILL for anything else the dead run left. The record goes to `meta.orphans`. A healing error is recorded there and doesn't stop the run. Processes without the id (the player's ./play, the app, other agents' tools) are never touched. Known limit: ./play launched by a GUI check through `open dist/Moonglade.app` doesn't inherit the id (LaunchServices), so it isn't healed and the GIVENs still refuse as before. Check: `report.orphans_healed` (full, stack down, about 45 s). (A) It SIGKILLs a nested `hs run --only play.loop_clean_exit` (test account, stand-in client) once its ./play, stand-in and worldserver are up; the run is SIGSTOPped first so its check can't stop the stand-in. The next nested run must record and stop them, its check passes, and nothing is left. (B) An untagged ./play (test account, stand-in) survives a run that heals another SIGKILLed run, and `play_checks.require_given_clear` still refuses while it runs.
- **Nightly (1.5):** `nightly.py`. Runs only on a clean `main` (fails closed on git errors), with no stack, ./play, Wine prefix process or other live harness run (from runreg), and not on battery below 35 %. If those hold, it does 3× `harness/hs run --tier full` and writes `harness/out/nightly/<date>/run<n>.json`, `nightly.json` and `flakes.md`: the runs, a summary line naming the flaky checks, and a table of their statuses. A skip writes the reason to both files and starts no run (exit 3). `--install` writes `~/Library/LaunchAgents/local.moonglade.nightly.plist` (03:00 daily, `harness/hs nightly`, log in env/logs/nightly.log) and bootstraps it into `gui/<uid>`; `--uninstall` boots it out and removes it. Not installed (task 3.2, Zach's call). Check: `report.nightly` (quick) uses stubbed runs and real scratch git repos. Its active-run case uses a real run file of a live `sleep`. Install and uninstall go to a scratch dir with launchctl stubbed, and the check asserts the real plist path is unchanged.

### B36 (task 2.1): target NOT met, measured best 2077–2087 s (limit 1500 s)
- **Measured first** (run 1, commit d444ef9, serial, 2026-10-08 01:21:32 → 01:56:09 UTC, wall **2077.1 s**). The screen was locked and the GUI rule says the GUI tier is due on this branch, so the preflight refuses an unfiltered `--tier full` run, and `--ignore-gui-preflight` was off-limits. Method: `--tier full` with `--only` naming every quick/full check that isn't GUI- or backups-marked, plus every post-run id. That's the same work as an unfiltered full run with both tiers skipped by design, except that `report.full_run` records skip. Time by phase:
  - ./play + Wine checks (stack-down GIVEN, order ≥ 300): 1420 s
  - stack-up phase: 394 s
  - `report.tiers` nested quick tier: 129 s
  - file-only checks: 73 s
  - build/lifecycle: 61 s
- **Resources.** Every ./play, Wine, real-client and stack check needs the one stack (mysqld, authserver and worldserver on fixed ports, the live acore_* schemas), the one Wine prefix and, for the real client, the screen. Each ./play check's GIVEN is "nothing running", and each starts and stops the whole stack itself (about 22 s to client-up, about 10 s to shut down). So those checks can't overlap one another, the stack-up phase or the nested quick tier. Inside the stack-up phase, the long checks restart the worldserver (era toggles, the baseline swap) or drive bots and the client, so nothing there can run alongside them either. What's left are file-only checks.
- **Side lane** (`hslib/sidelane.py`). `SIDE_LANE` lists 16 reviewed checks, each with what it touches: report.* rule simulations, repo.naming, repo.rename_script, client.config_gen, client.inspect, re.*, client.patch0001_recorded, client.play_build and client.play_revert.
  - They run in one worker process (`python3 -m hslib.sidelane`, its own environment and process group, killed as a group after 900 s), in (order, id) order, while the main lane runs only `PRE_BARRIER` checks. Those are the early report.*, build.*, core.* and setup/portable checks; none of them uses the stack, Wine, the screen or a port.
  - Before its first other check (lifecycle.failfast in full, lifecycle.up in quick), the main lane waits for the worker. A side check never overlaps a stack, Wine or screen check.
  - Records are merged and sorted by (order, id), so results.json and summary.md keep the serial order. Run 2 had the same id order as run 1.
  - `meta.schedule` records the mode, the side-lane ids, the worker's pid, exit, wall time, the main lane's wait and the barrier.
  - `hs run --serial` runs everything in the main lane. A `--serial` run's nested quick tier is serial too.
  - Recursion is impossible: `hs run` exits 2 under `$HS_SIDELANE_WORKER`, and the worker exits 2 inside another worker or outside `hs run`. Every nested `hs run` inside a check uses `--only <one check>`, so it never starts a worker.
  - The worker carries the run's `HS_HARNESS_RUN_ID`. After a SIGKILL of `hs run`, the next run's `runreg.heal()` stopped it (tested). The only thing left was its spec temp dir (`$TMPDIR/hs-sidelane-*`: check ids only).
- **Run 2** (commit c81013e, parallel, same filter method, 02:01:08 → 02:35:55 UTC, wall **2087.3 s**). The side lane took 56.8 s and the main lane never waited (0.0 s). Overlap was 43.8 s, and the nested quick tier was 19.9 s faster (128 → 108 s; quick alone 127.8 → 105.2 s). The long client/play checks, though, came in 62 s slower than in run 1 (run-to-run noise of ±5 s per check). Those checks start well after the side lane finished, so contention doesn't explain it. Net: no measurable change. Statuses were equal to run 1 for every check except report.coverage and report.tiers, which failed in run 1 only because `report.full_run_wall` wasn't registered yet.
- **`report.full_run_wall`** (`hslib/fullwall.py`; a post-run id in `reporting.POST_IDS`, so `report.coverage` knows it). It runs on unfiltered full-tier runs, before `report.full_run`, which counts it. `fullwall.finalize` re-judges it with the final `meta.wall_s`.
  - Modes:
    - strict: no GUI- or backups-marked check ran; `wall_s < 1500`.
    - adjusted: a GUI or backup path changed; wall_s minus those checks' time, which is an estimate. They run after the barrier, so nothing overlaps them.
    - serial-reference: a `--serial` run is recorded but not limited.
  - Statuses: every record except report.full_run_wall, report.full_run and report.timing must equal the other schedule's kept run of the same clean commit. A `--serial` full-tier run is also written to `harness/out/last-serial-full-run/`, and a parallel run compares against it; a serial run compares against `last-full-run/`. With no such run, the record says why (`status_reference.exists: false`). A dirty tree has no commit to compare.
  - A filtered run that names the check judges the kept last full run, or only runs its self-test if there is none.
  - Every record carries a 13-case self-test, and a wrong verdict fails the check. Cases include a fake 1600 s wall (FAIL), exactly 1500 s (FAIL), a status that differs from the serial run (FAIL), and reference lookup by commit and dirty tree.
  - `hs full-run-wall [results.json]` judges any results document and starts nothing.
- **Blockers to 1500 s.** About 1830 s of the 2077 s (88 %) is stack-, Wine- or screen-exclusive by the spec's own rule. Options, none taken here:
  1. A second isolated stack + Wine prefix (own datadir, ports, realmlist) for a parallel lane of ./play checks: the only route to a large cut. It's a big change to paths, ports, ./play and the client config; it needs its own change and ADR.
  2. Tighter readiness polling in `stack.py` (SOAP every 2 s, mysql/auth/stop every 1 s) and `play.py` (2 × 1 s client-exit debounce). Est. about 3 s per stack cycle × about 37 cycles ≈ 100 s. Both files are on the backups path list (play.py is also a GUI root), so touching them makes this change's verifier run the backups tier (+11 min). That's a decision for the orchestrator.
  3. Sharing one ./play session among several checks (as the GUI session already does). This changes what each check's GIVEN proves, so it needs a spec change.
