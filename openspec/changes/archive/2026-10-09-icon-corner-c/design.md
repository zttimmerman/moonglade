## Design
- **Mask.** Rasterise Apple's continuous-corner rounded rect as a closed outline. Use a well-documented reconstruction of the `cornerCurve = .continuous` path, such as the published UIBezierPath reverse-engineering curves (cite the source in the code), with analytic or supersampled coverage. This keeps the output deterministic across macOS versions.
- **Reference rendering.** A Core Animation render via ctypes, as in the preview script, is used only as the check's reference, with a tolerance. The generator doesn't use it.
- **Starting point.** The preview's helper scripts showed how variant C was rendered: a Core Animation mask via ctypes, passed to `render_tile(logo, mask=…)` with the default logo diameter.
- **What stays the same.** The navy gradient, glow, shadow parameters and logo diameter are unchanged from #29 (variant C used them). The shadow is derived from the mask, as `render_tile` already does.
- **Geometry from the record.** `app.icon` keeps taking its geometry from the `tile` record. Its `continuous…` envelope judgement stays, and it gains the reference-mask comparison and the 45° corner samples.

## As built (tasks 1.1–1.5, 2026-10-09)
- **Curve.** `icon.py` `CONTINUOUS_CORNER`: each corner is three cubic Béziers from (1.52866483 r, 0) on one side to (0, 1.52866483 r) on the other, with r first limited to body / 2 / 1.52866483. The source is "Drawing Code for iOS 7 Rounded Rectangles" (PaintCode/PixelCut, 2013-11-18, paintcodeapp.com/news/code-for-ios-7-rounded-rectangles), which gives the extent, the limit, every control point and the middle curve. There is one difference, and it was read from Core Animation itself. A `cornerCurve = continuous` CALayer (body 832, radius 216) rendered into a PDF context on macOS 26 emits exactly those curves, except that the outer curves end at the middle curve's ends, (0.63149399, 0.07491100) and its mirror. The 2013 code ends them at (0.66993427, 0.06549600) and adds a short line. With the 2013 end points, the mask differed from Core Animation by up to 145/255 at a pixel; with Core Animation's, by 12/255. Measured on 2026-10-09: the PDF path's points divided by 216 reproduce the constants to six digits.
- **Rasteriser.** `corner_mask`: the corner is flattened to 1024 points per cubic. Each pixel row is sampled at 16 heights. On each sample row the shape is one interval, and its exact overlap with each pixel is summed. It uses pure Python floats and no system calls, so it gives the same result on every macOS. It renders 1024 px in about 0.04 s. The same rasteriser draws circular-arc corners (`shape="circular"`), which the check uses for its counterexamples. The old analytic `rounded_rect_coverage` was removed (nothing else used it).
- **Geometry.** `TILE_SHAPE = "continuous"`, `TILE_BODY = 832`, `TILE_RADIUS = 216` (x0 = y0 = 96). The logo is cut at `ICON_DIAMETER × int(LOGO_REF_BODY × LOGO_SCALE) / CANVAS` with `LOGO_REF_BODY = 824`, which gives 569.719 px, the same as #29 and the preview. The `tile` record adds `shape_kind`, `corner_curve_ext` and `logo_ref_body_px`. Its `shape` text names the continuous curve, and `corner_radius_frac` is now radius / body (0.259615).
- **Compared with preview variant C.** That is `render_tile(logo, mask=<squircle.py 832/216>)`, regenerated from the scratch mask. Pixels more than 1 px from either outline's anti-aliased edge differ by at most 1 level, which is shadow rounding. Edge pixels differ by up to 67/255 in alpha. The preview's mask used `masksToBounds`, so Core Animation both clipped and filled the layer and its edge coverage came out squared (a half-covered pixel reads 0.29). That is Core Animation's compositing, not the shape.
- **Core Animation reference** (`harness/hslib/camask.py`, used only by `app.icon`). It runs in its own process (`python3 -I`), creates no LaunchServices registration (`lsappinfo` count unchanged), and renders the layer's own background without `masksToBounds`, so the coverage is linear. The generator's mask against it: mean 0.0067/255, max 12.1/255. The circular-arc mask of the same radius: mean 0.54/255, max 255/255, so it fails on the per-pixel limit. If Core Animation can't render the reference (missing script, rc ≠ 0, wrong byte count), `app.icon` fails and doesn't skip.
- **`app.icon` additions** (`verify_shape`):
  - **Record values.** The spec's literals: continuous, 832, 96/96, 216, logo 569.719, centred on 1024.
  - **Core Animation comparison.** The generator's mask must pass and the circular mask must fail.
  - **Probes**, built from the two masks. *Inside*: per corner, rays from the arc centre at 0°, 8°, 22.5°, 45°, 67.5°, 82° and 90°, taking the outermost pixel the continuous mask fully covers, which must be opaque navy. The 45° rays are the corner diagonals. *Gap*: every pixel fully inside the circular outline and fully outside the continuous one (992 pixels), whose alpha must be ≤ 128. The committed PNG's maximum there is 63, from the shadow.
  - **Built-in counterexamples.** A tile with circular 216 corners fails (the 45° pixels and the 992 gap pixels). The old 824 / 185.4 tile fails (the 0°/90° pixels where the sides begin, and 392 gap pixels).
- **Speed.** `tile_report` finds each row's run of pixels inside the band by formula and counts the alpha outside it with `bytes.count`. The per-pixel exact test still decides each row's two end pixels, and on the committed PNG and on perturbed and fully opaque images the count is identical to the old loop. `_deficit_sampler` uses `map(min)` plus `translate`, which gives identical bytes. `app.icon` went from 7.1 s to about 5.8 s.
- **Dev app.** `harness/hs app` rebuilt it once. The designated requirement is unchanged (`identifier "local.moonglade.app"`), and the bundle icon is byte-identical to `branding/AppIcon.icns`. In the tccd log from the rebuild through `app.dock_icon_rendered`, the Documents-folder request returned `authValue=2, authReason=2` (the existing grant). Other services were preflight denials by policy. There was no prompt.
