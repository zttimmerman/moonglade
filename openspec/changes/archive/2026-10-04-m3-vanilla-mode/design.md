# Design: M3 Vanilla mode

## Context
Gate 1 decisions and data from `docs/gate1-era-profile-memo.md`; tool `tools/era-diff`.

## Decisions
- **Data flow:** `tools/era-diff` gets `--emit-sql`, which writes `modules/mod-era-profile/data/sql/db-world/era_*.sql`: side tables with vanilla values plus source citation columns (snapshot, table, entry). It's regenerated, never hand-edited. `era.scope_guard` cross-checks the counts against the report.
- **Apply mechanism (in order of preference):**
  1. Runtime hooks: `OnPlayerQuestComputeXP` for quest XP (confirmed in the Gate 1 work). Other hooks get researched in AC's ScriptMgr (e.g. XP-for-level, creature template/HP selection, item/trainer requirements).
  2. Startup apply/revert. Where no hook exists, the module captures a baseline table once, then at server start writes either the vanilla or the baseline values for exactly the in-scope rows, before the world data loads. It's idempotent, so a crash mid-switch heals on the next start.
  3. A core patch only with an ADR.
- **Config:** `EraProfile.Enable` lives in the module's `.conf.dist` (default 1). `harness/hslib/config.py` renders it, and harness profiles can override it for the toggle checks.
- **Future:** keep the apply logic per entity and parameterised by mode, so a per-character runtime mode (the backlog menu) can reuse it.

## Risks
- What VMaNGOS `RewXP` means is unverified → must be confirmed before quest XP ships (proposal: Data provenance).
- Startup-apply races with world data load. → The module must run its apply in a hook that fires before the relevant ObjectMgr loads; verified by `era.default_on` and the spot checks.
- Death Knights level 55–59 slower (known, accepted at Gate 1).

### Startup apply/revert, as built
- **Side tables** (`era_<table>`), generated by `era_diff.py --emit-sql`: the key, the vanilla value per column (NULL = keep stock), and `src_snapshot` / `src_table` / `src_entry`. The files `DROP` and recreate the table, so a regenerated file replaces its table through the updater.
- **Baseline** (`era_baseline_<table>`, from `era_baseline.sql` with `CREATE TABLE IF NOT EXISTS` only, never dropped). At each start, before applying, the module copies the live stock value of every in-scope row that isn't captured yet (`INSERT IGNORE`, so the first capture wins). A row whose live value already equals its vanilla value is not captured and is logged as an error, because it isn't stock any more.
- **Apply** is one `UPDATE … JOIN baseline LEFT JOIN side`. Each captured row gets its vanilla value in mode 1 when the side table has one, and its baseline otherwise (mode 0, or a row dropped from a regenerated side table). It then **verifies** that 0 rows differ from what the mode wants and logs the counts (`[mod-era-profile] <table>: mode …, N side-table rows, N captured …, N rows at vanilla values, N rows differing`). The startup line is `Vanilla mode ACTIVE (EraProfile.Enable = 1)` only if every table verified and the quest table loaded. Otherwise it is `OFF` or `FAILED`. **Fail-closed:** a capture or verify query that returns no result counts as a failed verify (`COUNT(*)` always returns a row, so no result means the query failed). AzerothCore aborts the server on some MySQL errors (unknown column or table, parse error: `MySQLConnection::_HandleMySQLErrno`) but only logs the rest ("Unhandled MySQL errno") and returns no result. The module then logs `<table>: mode …: a capture/verify query failed` and `Vanilla mode FAILED`, never a `0 rows differing` count line, and `era.default_on` fails on either line.
- **Idempotent and crash-safe:** capture and apply are each one statement, and a re-run gives the same result.
- **Config:** `EraProfile.Enable` is read once in `OnLoadCustomDatabaseTable`. A later config reload only logs that a restart is needed (`OnAfterConfigLoad(reload=true)`), so quest XP and the table items can't drift apart.
- **era-diff and an applied world DB:** the diff reads `era_baseline_*` in place of live rows (`Ctx.overlay`), so it emits the same SQL from a stock DB and from a vanilla-applied one. `era.sql_deterministic` regenerates twice and byte-compares both runs with the committed files.
- **Accepted edges:** (1) If a future core DB update rewrites an in-scope row while vanilla is applied, the old stock value stays in the baseline. No core update touches `player_xp_for_level` today (grep of `data/sql/updates`). Re-check when bumping the core pin. (2) A changed side-table SQL file changes the module tree, and so the build-input hash, which forces a from-empty build at the next `hs build --clean`.

### Quest XP hook, as built
For quests in `era_quest_xp`, where the quest level still equals the row's level and AC's incoming XP is non-zero (so repeat completions and money-instead-of-XP stay AC), the hook **replaces** the XP with VMaNGOS `Quest::XPValue`: full `RewXP` up to 5 levels over, then `ceilf(float(RewXP) × 0.8f/0.6f/0.4f/0.2f/0.1f)`. It then applies AC's quest rate (truncated) and the `SPELL_AURA_MOD_XP_QUEST_PCT` multiplier, as `CalculateQuestRewardXP` does. Both era-diff mechanisms ("exact" difficulty and absolute) go through this table, which resolves memo Caveat A. Rows within ±5% of AC are left out (exact integer test `100·|vm−ac| ≤ 5·ac`). That leaves 1,855 of 2,261 change rows (406 within ±5%).

### Harness
- `harness/hslib/config.py` renders `etc/modules/mod_era_profile.conf` with a profile's `era` overrides. Only the new profile `wotlk` (m0 + `EraProfile.Enable = 0`) sets one, so the default profile tests the shipped default.
- `era.xp_curve` reads the XP needed for the next level from the running server. It changes the level with `.character level` and reads our own `PLAYER_NEXT_LEVEL_XP` update field from the probe, which now parses VALUES blocks of `SMSG_(COMPRESSED_)UPDATE_OBJECT`. `era.quest_xp` adds, completes and rewards each quest with GM commands and reads `SMSG_LOG_XPGAIN` plus `PLAYER_XP`. Both take their expected values from the VMaNGOS snapshot and from AC's base SQL or QuestXP.dbc at check time.

## Elite HP scope (task 2.3)
**Decision (orchestrator, 2026-10-03, from Gate 1 Decision 3 "Outdoor elites: restored together with their elite HP"; revised 2026-10-03 after the first M3 verifier pass):** every in-scope (outdoor, 1–60) creature whose **VMaNGOS rank is an elite rank** (1 elite, 2 rare-elite, 3 world boss; AC `SharedDefines.h` CreatureEliteType, same values in VMaNGOS) and whose VMaNGOS `health_multiplier` differs from AC's `HealthModifier` gets the **VMaNGOS multiplier verbatim**. Rank changes apply exactly as in the diff, including the one rare→normal case (2753). Implemented as era-diff category `elite_hp` (`cat_elite_hp`), which `--emit-sql` and `era.scope_guard` both read, so the counts below follow era-diff automatically.

**Why the multiplier transfers verbatim, at any level range.** Both cores compute HP as base HP[class, spawned level] × multiplier (AC `CreatureData.h:313-315` GenerateHealth). VMaNGOS `creature_classlevelstats.health` equals AC `basehp0` for every (class, level) pair at levels 1–60 (era-diff `creature_base_stats` has 0 health rows out of 180 pairs; memo #4). So the multiplier describes the same HP at every level, and a different level range between the cores doesn't stop it transferring. The first version took HealthModifier from `creature_stats` change rows, which marks 33 elites "needs-review (level range differs)"; those 33 kept stock HP while getting an elite rank. They now get the VMaNGOS value.

**The six formerly derived values (2647, 4844, 5647, 6213, 7872, 7874).** `creature_stats` proposes `VMaNGOS health[VMaNGOS class, level] × VMaNGOS multiplier ÷ AC basehp0[AC class, level]`, which reproduces VMaNGOS's absolute HP. For these six it differed from VMaNGOS's multiplier (3.0) because the two cores give the creature a **different `unit_class`**: 2647 is a warrior (1) in VMaNGOS and a paladin (2) in AC; the other five are mages (8) in VMaNGOS and paladins (2) in AC. Base tables are per class, so the ratio stopped being the multiplier (3.7509, 2.6819, 2.6242, 2.7741, 2.6994, 2.6994). VMaNGOS does provide a multiplier for them, and the requirement says the creatures SHALL have VMaNGOS's HealthModifier, so they now get 3.0 verbatim. The module never changes `unit_class`, so their absolute HP follows AC's class table: at the creature's minimum level, 2647: 5130 (VMaNGOS 6414); 4844: 3027 (2706); 5647: 4119 (3603); 6213: 1713 (1584); 7872 and 7874: 2784 (2505). The per-row note is in era-diff's `elite_hp` rows (`note` column).

**No creature ends up elite with stock HP where VMaNGOS's differs, with one exception.** 14442 Hunter Thunderhorn (L60, elite in both cores, so its rank is not changed) has AC `exp = 1`, so AC builds its HP on `basehp1` (4979 at L60, the TBC base table), not `basehp0` (3052, equal to VMaNGOS). VMaNGOS's 3.0 describes 3052 × 3 = 9156 HP; on `basehp1` it would give 14937, which is neither stock (19916) nor vanilla. Getting vanilla HP would need either a derived multiplier or changing `exp`, which is outside the module's columns. It stays stock and is flagged for the next human gate. `era.scope_guard` enforces the rule on the live rows: every in-scope creature with an elite rank in vanilla mode and an elite VMaNGOS rank must hold VMaNGOS's HealthModifier, and the only exemption is live `exp ≠ 0`, which it lists.

The 13 HP-only rows whose VMaNGOS rank is normal or rare (330, 1533, 2252, 2253, 2721, 2764, 2765, 3203, 3617, 4063, 4952, 8284, 11873) stay stock, as before: they are not elites in vanilla.

## Elites, mounts and riding, as built (tasks 2.3, 2.4)
Three more `APPLY_SPECS` lines in `EraProfile.cpp`: `creature_template` (`rank`, `HealthModifier`), `item_template` (`RequiredLevel`, `RequiredSkillRank`, `BuyPrice`) and `trainer_spell` (`ReqLevel`, `MoneyCost`, keys `TrainerId, SpellId`). ## Checks for tasks 2.3-2.5
- **GM inspection:** `era.elites` and `era.mounts` log in the harness's companion account HSCOMP (security 2, `hslib/companion.py`; never the PLAYER account), turn GM mode on, `.go xyz` to a spawn, wait until `.gps` shows the server has moved the character there (the teleport ack can be handled after later packets), then read `.npc info <spawnId>` (level, max HP), `CMSG_CREATURE_QUERY` (rank, HealthModifier as the client gets them), `CMSG_ITEM_QUERY_SINGLE` (tooltip level/price) and `CMSG_TRAINER_LIST` (the trainer window). The probe gained parsers for those three responses.
- **`era.elites`:** expected rank and HealthModifier from the VMaNGOS snapshot; expected max HP = AC's formula (`ceil(basehp × mod)` × `Rate.Creature.*.HP`) at the level the creature spawned with, using the VMaNGOS multiplier, and cross-checked against VMaNGOS `creature_classlevelstats.health × health_multiplier`. Out-of-scope creature: by rule, the lowest map-571-only creature with a base-SQL row that no world-DB update touches (5936 Orca at this pin); it must be absent from the module's tables and show its base-SQL rank, HealthModifier and HP.
- **`era.mounts`:** items from VMaNGOS `item_template`. Riding level/cost from era-diff's riding category (VMaNGOS trainer spells 33389/33392 matched to AC 33388/33391). The trainer is chosen by rule: the lowest trainer creature that lists both spells and Expert Riding, Artisan Riding and Cold Weather Flying (Spell.dbc names), which is 28746 (trainer 36) at this pin. The window's cost includes AC's reputation discount, so the check reads the character's rank with the trainer's faction (`.character reputation`) and applies `GetReputationPriceDiscount`. The three later riding skills must match the pinned base SQL, and every `trainer_spell` row of 33388/33391 must hold the VMaNGOS values.
- **`era.toggle_roundtrip` (full tier):** HSTEST is set to a known state with vanilla on: level 48, quest 10 rewarded (4,400 XP), fixture quest 7 incomplete in the log. Then `stack.ensure_profile("wotlk")` and back to `m0` (each restarts only the worldserver, ~20 s). In every phase the module's startup lines must show the right mode with 0 rows differing, and the GM character must see that mode's spot values: XP needed at level 20, quest 10's XP, item 2411's level and price, creature 678's rank. HSTEST's saved level, XP, inventory, quest log and rewarded quests must be identical to the known state. Afterwards HSTEST goes back to the fixture level with both quests removed.
- **`era.scope_guard` (full tier):** MySQL MD5 of every row (all columns, NULLs kept distinct) of the five touched tables, with vanilla off (`wotlk`), then on. The expected in-scope rows are rebuilt from era-diff's report rows (the category functions behind `report.json`: `outdoor_elite` for rank, `elite_hp` for HealthModifier), so the expected counts follow era-diff. The expectation: player_xp_for_level 49 rows, creature_template 233 (230 rank + 229 HP report rows, by entry), item_template 51 (101 field rows), trainer_spell 24 (4 riding report rows, 2 spells × 2 fields, on 12 AC trainers: 24 trainer/spell pairs), quest_template 0 (quest XP is a runtime hook). Out-of-scope rows must hash identically. The changed rows must be exactly the expected keys (count and set), changed only in the module's columns (`era_diff.BASELINE_COLS`), and hold the report's values. Two cross-checks that don't rely on the module: (1) with vanilla off, every in-scope row's module columns must equal the pinned core's base SQL (`data/sql/base/db_world/<table>.sql`, `era.stock_from_base_sql`), not the module's baseline table. Rows that a world-DB update statement may have changed are guarded and listed (`era.update_sql_touches`: the statement names the table and either names a module column or is a full-row INSERT/REPLACE/DELETE containing the key, or names a module column without the key column). At this pin no in-scope row is guarded, so all 357 are compared. (2) The elite-HP rule on the live rows (see "Elite HP scope").
- **Stock references:** `era.toggle_roundtrip`'s stock spot values (item 2411, creature 678), and the "stock" side of `era.elites` and `era.mounts`, come from the pinned base SQL with the same update guard, never from `era_baseline_*`. So a wrong baseline row, which the module would faithfully restore, fails the toggle check.
