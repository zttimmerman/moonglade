## Why
Prebuilt releases, part 2 of 3 (STATUS "Next", Zach 2026-10-07; split in `release-build`'s proposal). `release-build` makes a relocatable payload (server, MySQL, Python, harness, SQL) that runs without Homebrew, but nothing in it can play yet: the harness still assumes a git checkout, writes into the repo (`env/`, `data/`, `client/`), runs Homebrew's `mysqld` and the dev `vendor/` source tree, and the only way to set up is `./bootstrap` in a terminal. A friend who downloads the release needs to double-click Moonglade, point it at their own 3.3.5a client folder (bring your own client, ADR-0012) and end up playing, with no terminal, Homebrew or Xcode tools.

## What Changes
- **Two places, one resolver.** The app and everything shipped in it (APP) is read-only and can be moved, sit on a read-only volume or be translocated by Gatekeeper. Everything the friend creates (HOME = `~/Library/Application Support/Moonglade`) holds the MySQL data, rendered server configs and logs, server data (client-data), the Wine runtime and prefix, Moonglade's copy of their client and the play client derived from it, settings, `player.json` and backups. `harness/hslib/paths.py` resolves every path for both modes. A git checkout is always dev mode with today's layout, byte for byte.
- **Release mode in the harness.** Release servers get module keys as `AC_*` environment variables (ADR-0011's lane-B mechanism; the compiled-in config dir isn't usable from a read-only app). `SourceDirectory` and `MySQLExecutable` point into the payload (and `OPENSSL_CONF` is set), as `release-build`'s "As built" requires; the DB updater reads the payload's `sql/`; `mysqld`, `mysql` and `mysqldump` come from the payload's `mysql/`; Python is the payload's.
- **Release app shape.** The release zip's top level becomes `Moonglade.app`, with the `release-build` payload inside it at `Contents/Resources/Moonglade/` and the prebuilt launcher as `Contents/MacOS/Moonglade`. Signing, the icon tile and the Info.plist "not for redistribution" line stay in `release-signing` (3/3).
- **First-launch window** (in the launcher's existing loading-window style). On a first open it: checks this Mac (macOS, Apple Silicon, Rosetta, free disk up front), asks for the friend's own client folder (or zip), checks it is 3.3.5a build 12340 with the existing client inspection, copies what Moonglade needs into HOME (never writing to the folder they gave), downloads the pinned Wine runtime and server data with progress, sets up the databases, builds the play client, and finally tells them they can delete the folder they gave it. It is resumable and kill-safe, and every failure is a plain-language message with what to do.
- **Measurement.** The databases' first start is timed and split into SQL import vs bot setup, and recorded in design.md. No prebuilt database template is decided here.
- Harness checks for all of the above, run against a scratch HOME and a copy of `env/release`'s payload, under `release-build`'s no-Homebrew sandbox profile.

## Spec-change log
- 2026-10-08 (**loosening, flagged for the next human gate**; orchestrator decision 1, relabelled 2026-10-09 after the verifier's review): "no characters" in the safe database reset means no *player* characters. Reason: every first start creates the AI players' own characters on their `rndbot*` accounts (playerbots.conf.dist `RandomBotAccountPrefix`), so an interrupted first start always has some, and the original rule would never allow a reset after a kill during the database step. They don't count, and a character whose account is missing counts as a player's. The count is taken on an APFS clone of the datadir by a throwaway mysqld, never on the datadir itself. The requirement text and the "datadir with characters" scenario's GIVEN now say "player's character". It is a loosening of the written rule (a datadir with AI players' characters may now be reset); what a player made is still never reset. Exercised by `firstlaunch.kill_resume`: the database-step kill happens once AI players' characters exist (0 player characters) and the reset proceeds and setup finishes; a player's character keeps the datadir (`database_kept`, files unchanged).
- 2026-10-08 (clarification, orchestrator decision 2): the disk check runs in two places. Before the folder pick it checks room for the fixed part (the client's size isn't known yet); right after the pick, before anything is copied, it checks the full need (client size + fixed part). The requirement text says so; the scenarios are unchanged.
- 2026-10-08 (clarification, orchestrator decision 3): Moonglade's copy of the friend's client in HOME (`HOME/client`) keeps its write protection in release, like the dev `client/`. Removing Moonglade is documented in `docs/setup.md` ("Using a release"): Finder asks to confirm deleting locked items, or one Terminal line lifts the protection first. No spec text changes.
- 2026-10-09 (fix round 1, no spec text change; **flagged for the human gate**: adds deleting older set-aside datadirs with no player characters): set-aside datadirs (`mysql.unfinished-*`) no longer accumulate: only the newest is kept; an older one is removed only when the same no-player-characters rule (counted on a clone) says it is safe, never one holding a player's character (`docs/setup.md` "Using a release"). The release app refuses test switches up front unless it has the test hook, the flag, a scratch HOME and a harness run; when the payload's Python still refuses them (the run isn't live), the window names them in plain words.
- 2026-10-09 (**deviation from the THEN wording, stronger evidence; flagged for the next human gate**; fix round 2): scenario "Stack runs from the payload" says "the DB updater's log names the payload's `sql/`". AzerothCore's updater never logs the folder it reads: it logs only the file name (`DBUpdater.cpp:460`, `>> Applying '<file>'...`), and it runs the mysql client through `StartProcess(..., secure=true)` (`DBUpdater.cpp:558-559`), which turns off the argument trace. So the wording can't hold literally. `release.stack_from_payload` instead polls `lsof` on the payload's worldserver processes during `up` and requires every `.sql` file it had open to be under `APP/sql/`, and some of them to be files the log's "Applying" lines name. This observes what was actually read rather than what was logged, so it's stronger evidence, but it is not the written THEN; the scenario text is unchanged. One exact exception, found in fix round 2's slow run (lsof caught it once): the updater's own temporary `HOME/run/create_table.sql` (`DBUpdater.cpp:238-262`, CreateDatabase writes a one-line `CREATE DATABASE` query in its working directory, applies it and deletes it), accepted only at that path and only when the log says "Creating database"; it's written by the server, not read from any source tree.
- 2026-10-09 (**deviation from the GIVEN wording; flagged for the next human gate**; fix round 2): scenario "Player fingerprints unchanged" says the fingerprints are taken "at the start of the run". `release.player_data_untouched` takes them immediately before the first `release.*`/`firstlaunch.*` check of the whole run (lane A brought down first) and immediately after the last, because earlier dev checks (build, setup) legitimately write the live databases, so a run-start fingerprint would fail every run for reasons that have nothing to do with release mode. The bracket is planned over the whole run (every lane-A segment of a two-lane run; cycle 2 found it was per segment and so empty in two-lane runs), persisted under the run's output dir keyed by the run id, and checked against the run's actual execution log: nothing else may run inside it, lane B may not run during it, and if any release/firstlaunch check ran without a complete start+end pair the check fails naming what's missing. The scenario text is unchanged.
- 2026-10-08 (builder c, wording): the "can't read the folder" message now also says what Moonglade needs (3.3.5a, build 12340, English), as the "wrong clients are refused" requirement asks of every refusal; the "download damaged" message starts with a capital letter.
