## Context
`release-build` (1/3) made a relocatable payload; `release-first-launch` (2/3) wrapped it into `Moonglade.app` (`Contents/MacOS/Moonglade`, `Contents/Resources/Moonglade/<payload>`, bundle id `local.moonglade.release`) with a first-launch window. Its "As built" leaves to this change: bundle signing, the final bundle id and the payload's place, the icon tile and the Info.plist line, plus one finding: each scratch copy of the unsigned release app gets a new path-based privacy (TCC) identity, so checks avoid LaunchServices launches of it.

Today, file by file:
- `delocate.py` re-signs the server binaries and bundled dylibs ad hoc (`codesign --force --sign - --timestamp=none`), `release.py build_app_binaries` signs the launcher and `hsdock.dylib` the same way, python-build-standalone's `python3.13` is linker-signed ad hoc, and Oracle's `mysqld`, `mysql`, `mysqladmin`, `mysqldump` and `mysql/lib` keep Oracle's Developer ID signature with the hardened runtime and a timestamp (`codesign -dvv`: "Developer ID Application: Oracle America, Inc. (VB5E2TV963)", `flags=0x10000(runtime)`). The bundle itself is unsigned (`Sealed Resources=none`).
- The payload holds 29 Mach-O files (2026-10-08 build): the launcher (twice: `Contents/MacOS` and `bin/`), `bin/hsdock.dylib` (universal), `python/bin/python3.13`, one Python extension (`_dbm`), `server/bin/{authserver,worldserver}` + 14 dylibs in `server/lib`, Oracle's 4 programs + 3 dylibs (+2 dylib symlinks in `mysql/bin`). `libssl.3`/`libcrypto.3` exist twice (Homebrew's in `server/lib`, Oracle's in `mysql/lib`).
- The dev app (`harness/hslib/app.py`) is ad hoc with `designated => identifier "local.moonglade.app"`, and its Info.plist has `NSHumanReadableCopyright` = "Personal project; not for redistribution." The release plist (`release.py release_info_plist`) never had that line.
- The icon (`harness/hslib/icon.py`) is the gold ring cut out on a transparent background, 824 px across on a 1024 canvas (Apple's macOS icon grid). The shim gets `HSDOCK_ICON` from `launch.dock_env()`: the app bundle's `AppIcon.icns` in app runs, else `P.APP/branding/AppIcon.icns`; both come from `branding/`.
- The servers and mysqld bind 127.0.0.1 only (`config.py` BindIP, `stack.py` my.cnf), so neither mode triggers the macOS firewall's "accept incoming connections" prompt.
- The Wine runtime isn't in the app: first launch downloads it into HOME (`wine/runtime`) with Python's `urllib`, which sets no quarantine attribute. Moonglade never signs or changes it.

Sources used below (Apple documentation, read 2026-10-08):
- [A1] "Placing content in a bundle" (developer.apple.com/documentation/bundleresources/placing-content-in-a-bundle): code (Mach-O) goes in `Contents/MacOS`, `Contents/Helpers`, `Contents/Frameworks`, `Contents/PlugIns`…; resources (everything that isn't Mach-O, scripts included) in `Contents/Resources`; "incorrectly placed code might work during day-to-day development, but might cause problems during notarization"; each code location must be a flat list, and a directory name with a dot inside a code location is treated as a bundle and fails to sign.
- [A2] "Hardened Runtime" (developer.apple.com/documentation/security/hardened-runtime): notarization requires it; entitlements go only on executables, libraries inherit the host's; use only the exceptions that are needed; exception keys `com.apple.security.cs.allow-jit`, `…allow-unsigned-executable-memory`, `…allow-dyld-environment-variables`, `…disable-library-validation`, `…disable-executable-page-protection`.
- [A3] "Resolving common notarization issues": sign with Developer ID Application; secure timestamp (`--timestamp`, needs network to timestamp.apple.com); hardened runtime (`--options runtime`); no `get-task-allow`; entitlements as an XML plist (not `bplist00`); verify with `codesign --verify --deep --strict` (strict matches notarization); `spctl --assess` shows the policy result.
- [A4] "Customizing the notarization workflow": the notary service accepts UDIF disk images, flat installer packages and ZIP archives; "While you can notarize a ZIP archive, you can't staple to it directly. Instead, run `stapler` against each item that you added to the archive. Then create a new ZIP file containing the stapled items."
- [A5] "Notarizing macOS software before distribution": the ticket is published online and may be stapled; Gatekeeper finds either.
- [A6] Apple Support "Safely open apps on your Mac" (support.apple.com/102445): an app that isn't notarized is opened via System Settings → Privacy & Security → "Open Anyway" after a first blocked attempt (since macOS 15 the Control-click → Open shortcut no longer bypasses this).
- [A7] TN3127 "Inside Code Signing: Requirements": the designated requirement is what TCC and keychain use to decide "same app"; Apple's default for Developer ID code is identifier + Apple anchor + the Developer ID leaf + team OU.

## Goals / Non-goals
- Goals: both signing modes built and checked to the extent possible without Apple credentials; switching is one line; a final bundle id; the navy icon everywhere; the plist line gone; friends get plain instructions.
- Non-goals: buying the Developer Program (Zach's call); a DMG (later, see decision 5); auto-update; signing or notarizing the downloaded Wine runtime (not shipped by us); an installer package; changing the payload's layout unless notarization requires it (decision 2's fallback).

## Decisions

### 1. Mode setting and packaging steps
- `tools/release/signing.json`: `{"mode": "ad-hoc"}`. Allowed: `ad-hoc`, `developer-id`. `release.py --signing-config <file>` (checks only) reads another file; it is accepted only for files under `env/release/` or `harness/out/` so a stray flag can't redirect a CI build.
- New module `tools/release/sign.py` and two release.py steps, so the order becomes `clean fetch build payload sign assets notarize`:
  - `sign` (both modes): reads the mode; in `developer-id` mode first checks the credentials (decision 5's names) and fails listing the missing ones before touching anything, and refuses outside `GITHUB_ACTIONS=true`. Then signs inside out (decision 3), verifies, and writes `env/release/build/sign.json` (mode, identity kind, per-file identifier, cdhash, flags, entitlements hash, Oracle files' original cdhashes, the bundle's designated requirement, the environment keys it read).
  - `notarize` (`developer-id` only; a no-op recorded as "not applicable" in `ad-hoc`): submits the zip made by `assets`, waits, saves the notary log JSON to `env/release/build/notary-log.json`, fails unless `Accepted` with `issues` empty or null, staples the app, `stapler validate`, re-zips with the same `ditto` flags, rewrites `SHA256SUMS` and `SOURCES.json`'s zip entry.
- `assets` zips the signed app (it already uses `ditto -c -k --keepParent --norsrc --noextattr --noqtn`; signatures live inside the Mach-O files and `_CodeSignature/`, so dropping extended attributes is right: nothing we sign may depend on an xattr signature, which is why decision 2 forbids non-Mach-O files in code locations).
- Local builds keep the "local test build, not for publishing" label (release-first-launch 5.4) in both modes; local `developer-id` is refused, so a local zip is never Developer ID signed.

### 2. Bundle id and layout
- **Bundle id `io.github.zttimmerman.moonglade`.** Reverse DNS of the GitHub Pages domain of the account the source is published under (a domain the owner controls, the usual rule for bundle ids). Distinct from the dev app's `local.moonglade.app`, so TCC grants, LaunchServices records and Gatekeeper approvals never mix between Zach's dev app and a release copy. Changing it after friends install would make macOS see a new app, hence "Choices for Zach" 2. Nested code gets identifiers `io.github.zttimmerman.moonglade.<file name>` (e.g. `….worldserver`), so `codesign -dv` output is self-explanatory; Oracle's keep theirs.
- **Layout: keep the payload at `Contents/Resources/Moonglade/`, sign each Mach-O on its own (recommended).** Reasons:
  1. [A1] says code in Resources "might cause problems during notarization", not that it is rejected. The concrete problems are that `codesign --deep` doesn't sign code there and that bundle verification seals it as data only. Both are handled: we sign every Mach-O explicitly, inside out, with the hardened runtime and (developer-id) a timestamp, and the checks verify every file on its own as well as the bundle. The notary service inspects every Mach-O in the submission wherever it sits and tickets each cdhash [A4, A5]. Signed native code under `Contents/Resources` is routine in notarized apps (e.g. Electron apps' `app.asar.unpacked` native modules).
  2. Moving code to `Contents/Helpers` / `Contents/Frameworks` is expensive here: code locations must be flat [A1], but the payload has two different `libssl.3.dylib`/`libcrypto.3.dylib` (Homebrew's for the server, Oracle's for MySQL); Oracle's binaries load `@loader_path/../lib`, so moving them means `install_name_tool` edits and discarding Oracle's signature; and python-build-standalone finds its standard library from the real (symlink-resolved) directory of its executable (CPython 3.13 `Modules/getpath.py`: `executable_dir = dirname(realpath(executable))`), so a moved `python3.13` needs a `python3._pth` next to a symlink in Resources. Every `release.*`/`firstlaunch.*` check and the resolver would change with it.
  3. The data tree contains directories with dots (`python/lib/python3.13`), which may not sit in a code location [A1]; it can stay in Resources only if code and data are split.
- **Arbiter and fallback.** The first `developer-id` run is the proof: `notarize` fails on any notary issue, before a draft exists. If the notary service or Gatekeeper objects to code in Resources, the prepared fallback (follow-up change, not built here) is: executables to `Contents/Helpers/` (flat; `mysqld` etc. re-signed by us), dylibs and the Python extension to `Contents/Frameworks/` (flat; the two OpenSSL copies resolved by linking the server against Oracle's 3.x or renaming one with a matching install name), symlinks left at the old payload paths, `python3._pth` beside the Resources-side `python/bin/python3` symlink (CPython 3.13 reads `<executable>._pth` from the unresolved executable path too), and `paths.py` adding a `CODE` root for the executables. `signing.bundle_layout`'s allowed-places list is the one thing a fallback would edit in this change's checks.
- Nothing writes into the bundle at runtime (release-first-launch already runs Python with `-B` and keeps all state in HOME); `signing.seal_survives_use` proves the seal still verifies after first launch and play.

### 3. Hardened runtime and entitlements
- Both modes sign every executable we sign with `--options runtime`, so the hardened runtime that `developer-id` requires [A2, A3] is exercised by every local check (the release checks run the signed fixture app), not only in CI.
- Roles and entitlement files (`tools/release/entitlements/<role>.plist`, XML, only `true` keys [A2]): `launcher` (`Contents/MacOS/Moonglade`, `bin/Moonglade`), `python` (`python3.13`), `server` (authserver, worldserver). Libraries (`*.dylib`, `*.so`, `hsdock.dylib`) get none: they inherit the host's [A2]. No `get-task-allow` ever [A3].
- **Starting expectation, to be measured (task 2.2), never assumed:**
  - launcher: none. Cocoa app, spawns the payload's Python; no JIT, no plug-ins.
  - server: none. Plain C++; loads only our re-signed dylibs.
  - python: possibly `com.apple.security.cs.disable-library-validation` in ad-hoc mode only (if the hardened runtime refuses to let an ad-hoc process with no Team ID load the ad-hoc `_dbm` extension; `_dbm` is unused by the harness, so dropping it from the payload is the better fix if that is the only failure), and possibly `…allow-unsigned-executable-memory` if `ctypes` needs writable+executable memory. Today `ctypes` is used only for calls (`clonefile`, libproc, sysctl), not callbacks, so neither is expected.
  - Not needed by design: `…allow-dyld-environment-variables`. The play loop puts `DYLD_INSERT_LIBRARIES` (the shim) and `DYLD_LIBRARY_PATH` into the environment of the Wine process it starts. dyld honours or prunes `DYLD_*` in the process being started, judged by that process's own signature; the Wine runtime isn't hardened (downloaded, never signed by us), so the hardened Python parent doesn't matter. `release.client_smoke` and `release.play_standin` run the signed app, so a wrong expectation fails them.
- Method (task 2.2): sign with no entitlements, run the release smoke, `firstlaunch.flow`, `release.play_standin` and `release.client_smoke` from the signed fixture; for each failure add the narrowest key, recording the failure text. Each key that ends up in a file gets a line here (key, role, the flow that fails without it, the error) and is kept honest by `signing.entitlements_needed`.
- If ad hoc needs a key that Developer ID doesn't (library validation can differ without a Team ID), the file gains a per-mode section and this section records why; the first `developer-id` run's smoke (on the signed app, before notarization) is where the Developer ID set is proven.
- Oracle's MySQL files keep Oracle's signature in both modes: valid Developer ID, hardened, timestamped, so notarization accepts them [A3] and their provenance stays visible. `release.py` records their cdhashes at `payload`; `signing.adhoc_signature` asserts they are unchanged.

### 4. Designated requirement and privacy grants (TCC)
- `ad-hoc`: `-r='designated => identifier "io.github.zttimmerman.moonglade"'` on the bundle, like the dev app. An ad-hoc signature's default requirement is its code hash, which changes with every build, so every update would count as a new app for TCC [A7]. Pinned to the identifier, a grant survives updates and copies.
- `developer-id`: no override; codesign's default Developer ID requirement (identifier + Apple anchor + Developer ID leaf + team) [A7] survives updates and can't be matched by anyone without Zach's certificate.
- What a release needs from TCC: one folder-access grant when first launch reads the friend's client folder (often in Downloads or Documents). After setup everything is in `~/Library/Application Support/Moonglade`, which needs no grant, and loopback networking needs none. So in practice a friend sees at most one privacy prompt, normally only once.
- **What ad hoc can't do** (written into `docs/setup.md` in plain words where it matters to a friend):
  - Gatekeeper approval doesn't carry over: each new version arrives quarantined with a new code hash and needs "Open Anyway" again [A6].
  - The identifier-only requirement proves nothing about who built the app: any ad-hoc app claiming the same identifier would inherit the grant. Accepted because the only grant at stake is read access to the folder the friend picked for the game; with `developer-id` this goes away.
  - No notarization ticket, so Gatekeeper's malware scan result isn't available; `spctl` rejects it (`signing.gatekeeper_adhoc` records the exact text).
- Side benefit for checks: a bundle-signed release app has a stable TCC identity, so after a one-time grant scratch copies could be launched through LaunchServices. The checks keep running the launcher binary directly (release-first-launch "As built"); nothing here depends on a grant.

### 5. Developer ID: credentials, notarization, container
- Repo secrets (names only; values never logged; `sign` checks presence first):
  `MOONGLADE_DEVID_P12_BASE64` (Developer ID Application certificate + key, .p12), `MOONGLADE_DEVID_P12_PASSWORD`, `MOONGLADE_DEVID_IDENTITY` (e.g. `Developer ID Application: Name (TEAMID)`), `MOONGLADE_TEAM_ID`, `MOONGLADE_NOTARY_KEY_P8_BASE64`, `MOONGLADE_NOTARY_KEY_ID`, `MOONGLADE_NOTARY_ISSUER_ID`.
- Notary credentials: an App Store Connect API key (Developer role) via `notarytool submit --key --key-id --issuer`, recommended over an Apple ID + app-specific password: it is scoped, revocable on its own and doesn't involve the Apple ID's password or two-factor login.
- Keychain: the workflow creates a temporary keychain with a random password, imports the .p12 (`security import … -T /usr/bin/codesign`), sets the partition list, prepends it to the search list, and deletes it in an `if: always()` step. Files decoded from secrets go to `$RUNNER_TEMP` and are removed in the same step.
- **Container: notarized zip with the stapled app inside (recommended).** Same asset shape in both modes, so the size gate, `release.no_game_files`, the smoke step and first launch don't change; `ditto` preserves everything the signature needs; the ticket is stapled into the app [A4], so it travels after unzipping and works offline. A DMG would give the drag-to-Applications picture and a ticket on the disk image itself, but adds `hdiutil` building and signing, a second container to check, and first launch already copes with translocation. Revisit if friends ask.
- Sequence in CI: package → `sign` → smoke (no Homebrew, signed app) → `assets` (zip) → `notarize` (submit, wait, log, staple, validate, re-zip, sums) → `spctl --assess` on a fresh unzip (`signing.notarized`) → draft release with `tools/release/notes/developer-id.md`.

### 6. Icon: navy tile everywhere

Geometry, colour and logo scale are recorded in `AppIcon.json` (`tile`: size, corner radius, navy RGB, logo diameter); checks read them from there.
- Values: the navy and the logo scale come from Zach's approved mockup (not in the repo or session records; task 3.1 asks Zach or proposes values and shows a preview). The corner radius comes from Apple's macOS app icon template (Apple Design Resources); task 3.1 records the source, or flags it in the proposal if it can't be sourced.
- Everything uses `branding/AppIcon.icns`: the dev app (`app.py`), the release app (`release.py wrap_app`), and `launch.dock_env()` (bundle icon in app runs, `branding/` otherwise). No new code path; the checks prove it by pixels.
- The shim, in test mode only (`HSDOCK_TEST=1`), logs after loading `HSDOCK_ICON`: the image size and the RGBA it reads at the points named in `HSDOCK_ICON_SAMPLES` (fractions of the image: centre, a canvas corner, tile-edge points). `app.dock_icon_rendered` derives the points from `AppIcon.json` and compares. Normal runs log only what they log today.
- The dev app's designated requirement is unchanged, so rebuilding it with the new icon and plist shouldn't trigger new privacy prompts (one at most).

## Risks / Trade-offs
- **Code in Resources** (decision 2): accepted on evidence and precedent, with the notary log as arbiter and a designed fallback. Cost if the fallback is needed: one follow-up change touching the layout, the resolver and the release checks' paths.
- **Unknown Developer ID entitlement differences** (decision 3): caught by the CI smoke on the signed app before notarization; nothing is published on failure.
- **Ad-hoc identifier-only requirement** (decision 4): weaker identity, limited to the folder grant; documented.
- **Secrets in a public repo's workflow**: tag-push triggered only, never on `pull_request` from forks; secrets go only to steps behind the mode condition; the keychain and decoded files are removed in `always()` steps; `signing.mode_setting` parses the workflow for these properties.
- **Icon on macOS 26**: whether the system adds a plate to a full-tile `.icns` is judged by Zach (human-verify). If it does, an Icon Composer `.icon` asset is a follow-up.

## Approved navy tile (orchestrator, 2026-10-08; recovered from the mockup Zach chose)
Zach picked "Dark navy tile" from a 4-way mockup (white / navy / black / borderless) rendered from `branding/AppIcon.png`. Its parameters, per N×N canvas (N = 1024 for the master):
- Tile body: `N*824/1024` square, centred; corner radius `body*0.225` (rounded rectangle; replace with Apple's template squircle only if the preview still matches, and show Zach both).
- Fill: vertical gradient, top → bottom, RGB `(28,38,62)` → `(18,24,38)` (i.e. `(28-10t, 38-14t, 62-24t)`, t = y/N).
- Glow: ellipse over `[0.2N, 0.2N, 0.8N, 0.8N]`, RGBA `(90,120,170,110)`, Gaussian blur radius `0.08N`, composited over the gradient.
- Shadow: tile mask blurred 10 px (at N=512; scale with N), alpha ×0.35, offset 6 px down (scale with N).
- Logo: `branding/AppIcon.png` scaled to `body*0.86`, Lanczos, centred.
